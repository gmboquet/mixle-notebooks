## 9. Rollback readiness

This repository has no package to un-publish and no running service to roll back — "shipping" here
means the `release/0.7.0` branch is merged to `main` and (optionally) tagged. If a problem surfaces
after that merge — a notebook that was actually broken, a data file that shouldn't have been
committed, a path leak this pass missed — the rollback is a `git revert` of the merge commit (or of
the specific offending commit, if isolating it is cleaner) on `main`, pushed normally; there is
nothing to unpublish externally, no cached artifact on a package index, and no downstream installs to
notify, because nothing outside this git repository depends on a specific commit here. If the docs are
deployed to GitHub Pages, that deploy would need a follow-up rebuild from the reverted tip, since a
stale published page is otherwise the only externally-visible artifact that could outlive a revert.
The one thing a revert cannot undo is a `v0.7.0` tag someone has already pulled and built against
directly (rather than through `pip install mixle-pde`-style resolution) — which is exactly why tagging
is deliberately left to the release owner's sign-off (§11), not automated here. No action needed for
this pass beyond writing this down.
